# Phase 5 Incremental Execution Plan

## Why this doc exists

`tools-backlog-longtail.md` explicitly recommends against building its ~707 remaining tools wholesale. Prior sessions picked from it in a couple of larger opportunistic batches (25-30 tools each, built and shipped in one go). Per the user's request (2026-09), this replaces that approach with **smaller increments, one batch reviewed and committed before starting the next**, rather than chaining many large batches in a single sitting.

## Method

- `tools-backlog-longtail.md` is already sorted by monthly volume descending, then unresearched entries at the bottom — work through it **top to bottom, in batches of ~15 tools**, rather than re-sorting thematically. This keeps each batch's tools roughly similar in value and keeps the method mechanical/repeatable rather than requiring fresh curation every time.
- Each batch: pick the next ~15 rows off the top of `tools-backlog-longtail.md`, build them via the site's standard 3-file pattern (same as every prior phase), verify (`tsc --noEmit` + the duplicate/orphan registry audit script + a content-quality spot-check on each new file), remove the built rows from `tools-backlog-longtail.md`, update `existing-tools-inventory.md`'s count, commit and push to `main`.
- ~707 tools ÷ ~15/batch ≈ 47 batches total at this pace. This doc's Progress Log tracks how many have actually shipped — it is not a pre-written schedule of all 47 batches' exact contents, since curating that far in advance isn't useful (the next batch is always just "the next ~15 rows in the file").
- Near-duplicates of already-live tools are expected to keep showing up (as they have in every phase so far) — same standing policy: build as a separate, genuinely differentiated page targeting the distinct keyword, not skipped, per the user's earlier explicit decision on this (see `tools-gap-analysis-roadmap.md`'s Source & Methodology section).

## Build verification note (2026-09)

`npm run build` fails locally on this machine with a deterministic `spawn EBADF` error during static-page generation — a known macOS-specific Next.js 15.x regression ([vercel/next.js#78276](https://github.com/vercel/next.js/issues/78276)) that reproduces identically across Node 20/22, Next 15.5.15/15.5.25, and every worker-concurrency setting tried. It is not a code issue (`tsc --noEmit` and the webpack compile step both pass cleanly every time) and is not fixable from the repo side. Per the user's direction, per-batch local verification is `tsc --noEmit` + the registry audit + content-quality checks, with the real full `npm run build` check happening via GitHub Actions CI — which only runs on push to the `deploy` branch (`.github/workflows/deploy.yml`), not on every `main` push. Merge `main` into `deploy` and push periodically (not necessarily after every single batch) to get a real CI build confirmation and ship the accumulated batches live; batches 6-15 (139 tools) were confirmed via this method on 2026-09-05 (CI run succeeded, site confirmed live by the user).
